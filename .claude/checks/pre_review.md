# checks/pre_review.md — 评审前自检清单

> **用法**：在请 `reviewer` 之前，**先自己过一遍**。
> 目的：**别把明显的问题送去评审** —— 那会浪费评审的可信度，也拖慢流程。
>
> 评审前的自检**比评审本身更重要**：reviewer 的价值在于发现你想不到的问题，
> 不是替你发现你没检查的问题。

---

## 0. 30 秒版（最小必查）

```bash
git status --porcelain          # 有没有误改的文件、误提交的产物
git diff --stat                 # 改动范围是否符合预期（有没有顺手扩大）
node .claude/scripts/check_system.mjs   # 若改了 .claude/ 系统
```

**三个必答问题**：
1. 改动范围**是否就是计划的范围**？（有没有"顺手"）
2. **变更记录**做了吗（真重要变更 → commit message 一行；业务规则 → `business-logic.md`；结构 → `CLAUDE.md`）？
3. 有没有**我不确定**的地方？（→ 写进「待确认」交给 reviewer/用户，**别装作确定**）

## 1. 完整自检（按流程类型）

### 1.1 feature 流程 → 自检五道闸门

| 闸门 | 自检项 | 过? |
|---|---|---|
| **契约确认** | 每个接口的路径/入参/响应/错误码都有出处（后端文档）？无臆造？ | ☐ |
| | `endpoints.js` 已登记？`api/<域>.js` 已导出？`api/index.js` 已加 export？ | ☐ |
| | 每个 `options` 默认值都写了 why？ | ☐ |
| **分层达标** | 业务逻辑**不在** `pages/` / `components/`？ | ☐ |
| | 依赖方向只向下？无环（或环已用注册模式解）？ | ☐ |
| | 未重造 `useList` / `useModal` / `usePullRefresh` / `platform` / `storage`？ | ☐ |
| **测试覆盖** | 关键失败路径（`ApiError` 各 type）有用例？ | ☐ |
| | 边界有用例（空值 / 0 / 超长 / 非法类型）？ | ☐ |
| | **未覆盖清单**已如实列出？未伪造覆盖率？ | ☐ |
| **安全通过** | `security_agent` 无严重/高风险？ | ☐ |
| | 每个 `guard:false` 都有合法理由？ | ☐ |
| **评审通过** | 无阻断项？ | ☐ |
| | **变更已记录**（真重要变更 → commit 一行；业务规则 → business-logic.md；结构 → CLAUDE.md）？ | ☐ |

### 1.2 bugfix 流程 → 自检四道闸门

| 闸门 | 自检项 | 过? |
|---|---|---|
| **根因确认** | 根因收敛到**一处**，一句话说清？ | ☐ |
| | 证据链含 `file:line` 或命令输出（非纯叙述）？ | ☐ |
| | 「已排除的假设」表已填？ | ☐ |
| | 无法本地验证的已标「未确证」？ | ☐ |
| **最小修复** | 改动范围 = 根因报告的最小方案，**未扩大**？ | ☐ |
| | 未顺手重构 / 未改格式化 / 未动不相关文件？ | ☐ |
| | 未碰 `src/uni_modules/`？ | ☐ |
| | 修的是**根因**不是症状（未用 try/catch 吞、未加延时）？ | ☐ |
| **回归覆盖** | 回归用例覆盖了本次根因的触发条件？ | ☐ |
| | 已排查「同一根因模式是否在别处也存在」？ | ☐ |
| **登记** | `memory/bug_history.md` 已补条目（含**防复发措施**）？ | ☐ |
| | 若属真重要变更（口径 / 权限等），commit message 已写一行？ | ☐ |

### 1.3 refactor 流程 → 自检核心闸门

| 闸门 | 自检项 | 过? |
|---|---|---|
| **必要性** | 重构动机有**当下需求**支撑（不是「架构好看」）？ | ☐ |
| **行为基线** | 改动前的**可观察行为**清单已列出（含错误路径与边界）？ | ☐ |
| **行为等价** | ★ 基线清单**逐条**都有改后对照结论（无遗漏项）？ | ☐ |
| | 错误路径与边界也在对照表内？ | ☐ |
| | 无法验证的已标「未确证」？ | ☐ |
| **未触契约** | 导出签名 / 接口路径 / 字段名 / 错误码**均未变**？ | ☐ |
| **无夹带** | 没有顺手夹带的行为变更？（有 → 整单打回重走 feature） | ☐ |

## 2. 送评审时的信息包（**这些都要给 reviewer**）

```
【评审范围】git diff / 指定文件 / 指定模块
【改动意图】一句话说清本改动要达成什么
【已自检】贴 pre_commit.md 的 A/B/C 段命令输出
【已知不确定】<列出来 —— 诚实声明比假装完整更有价值>
【明确排除】<不报什么，如"样式微调不用报">
【期望结论】通过 / 有条件通过 / 打回
```

## 3. 特别提醒（本项目高频漏项）

| # | 高频漏项 | 后果 |
|---|---|---|
| 1 | **改结构没同步 `CLAUDE.md`** | `reviewer` 阻断 |
| 2 | **真重要变更没写进 commit message / 业务规则没更新 `business-logic.md`** | `reviewer` 阻断 |
| 3 | 修 bug 没补 `bug_history.md` | 同一 bug 会二次出现 |
| 4 | 忘了在 `pages.json` 登记新页 | 页面打不开 |
| 5 | 忘了在 `api/index.js` 加 export | 引入报错 |
| 6 | 新页漏挂全局 `<app-loading>` / `<app-modal>` | 静默降级 / 弹窗不弹（BUG-003/004） |
| 7 | 类名撞 ColorUI | 真机布局坏（BUG-001） |
| 8 | 改了 C 端共用文件却没标注 | 双端不一致 |
| 9 | 没写 why 注释 | 可维护性下降，reviewer 会提 |
| 10 | 列表有可写子页却没接 `dirtyKey`，或子页写成功后没 `markListDirty` | 返回列表吃旧数据 / 无条件重拉闪一下（v1.2.2 口径） |
| 11 | 页面里自己写 loading 延时 / 最短驻留 | 与全局节奏打架，观感不一致（统一在 `services/toast.js`） |

## 4. 什么时候**不该**送评审

| 情况 | 先做什么 |
|---|---|
| 自己都知道有阻断项 | 先修，别浪费评审 |
| 契约不确定 / 字段是猜的 | 先问后端（`api_designer`） |
| 变更记录没做 | 先按 §11.1 记录（D 段） |
| 改动范围明显超计划 | 先收窄 |
| 测试没生成 | 先让 `test_agent` 出用例清单 |

## 5. 评审后

| reviewer 结论 | 处理 |
|---|---|
| 通过 | 继续 |
| 有条件通过 | 建议项登记到 `known_issues.md`，**可延后但不遗忘** |
| 打回 | 按阻断项归属退回对应阶段，**不许带病前进** |

**复评时**：只复审上次的阻断项 + 确认修改未引入新问题（尤其未顺手扩大范围）。
