# prompts/task_opening.md — 任务开场提示词

> **用途**：开一个新任务时，用这些片段把「需求 → 可执行的 AI 任务」补齐。
> **核心原则**：**没有验收标准的任务，AI 一定会发散。**

---

## 1. 万能开场模板（复制即用）

```
【任务】<一句话目标>
【类型】feature | bugfix | refactor | release | 简单改动
【范围】<涉及模块/页面/接口；不确定就写"待你判断">
【约束】<后端契约有没有到位、能否改 endpoints.js、是否需要兼容 C 端、
        能否引入新依赖、是否需要保持与现网风格一致>
【验收】<怎么算做完 —— 必须具体、可判定>
【不做】<明确排除的部分，避免顺手扩大范围>
```

## 2. 按类型的开场示例

### 2.1 feature（新功能）

```
新增「车辆管理」列表页：分页、下拉刷新、点进详情。
走 feature 流程。

约束：
- 后端契约已到位（附文档）：GET vehicle/list，page/page_size，
  响应 data.list/data.total
- 准入是「公开 / 仅需登录态」（不会回 40102），故**不加**前置权限检查
- 页面风格照抄 pages/admin-home 的 B 档页壳
- 不要引入新依赖

验收：
1. src/config/endpoints.js 已登记 ENDPOINT_VEHICLE_LIST
2. src/api/vehicle.js 导出 vehicleApi，api/index.js 已加 export
3. 页面用 useList + app-list-state，无手写分页
4. pages.json 已登记
5. reviewer 无阻断项
6. 真重要变更已在 commit message 写一行；业务规则已同步 `business-logic.md`（见 §11.1）

不做：详情页（本次只做列表）、筛选栏
```

### 2.2 bugfix（缺陷）

```
【现象】登录页点「去绑定手机号」后返回，绑定态仍显示"未绑定"。
        微信小程序真机，production 环境。
        期望：绑定后返回显示"已绑定"。实际：仍显示"未绑定"。
        无报错。

【类型】bugfix
【验收】debugger 给出根因（需 file:line 证据，不许猜）
        → 确认后再修 → test_agent 补回归 → reviewer 通过
        → 补 memory/bug_history.md（仅真重要变更才写 commit 一行）

先别改代码，只要根因报告。
```

### 2.3 refactor（重构）

```
把 pages/admin-home 里手写的 refreshBound 取数逻辑换成 useList 形态。
走 refactor 流程。

【验收】行为等价 —— 需要逐条对照改动前后的可观察行为（含失败路径与边界）。
        reviewer 确认无夹带的行为变更。

注意：该页是「状态展示位」不是列表页，useList 的分页语义可能不适用。
      如果 architect 评估后认为不该换，说清理由即可，不要硬换。
```

### 2.4 release（发布）

```
发布微信小程序生产包。

【验收】
1. reviewer 已通过（无阻断项）
2. security_agent 无严重/高风险
3. 真重要变更已在 commit message 记录（CHANGELOG 已冻结）
4. 构建命令序列最后一条是 build:mp-weixin
5. grep localhost:15200 dist/build/mp-weixin/ 为空
6. 给出回滚方案

⚠️ 执行任何构建命令前先告诉我你要跑什么。
```

### 2.5 简单改动（**不走流程**）

```
改一下登录页副标题的文案：从「后台管理端」改为「管理后台」。
直接改，不用走流程。
```

## 4. 反模式（❌ 不要这样开场）

| ❌ 差的开场 | 为什么差 |
|---|---|
| 「优化一下代码」 | 没有目标、没有验收，AI 会乱猜 |
| 「看看有没有问题」 | 同上；且会触发无边界扫描 |
| 「加个车辆管理」 | 没说范围（列表还是详情？）、没说验收 |
| 「按最佳实践重构一下」 | 「最佳实践」是空话，且重构需要行为基线 |
| 「顺便把样式也调一下」 | 「顺便」= 范围蔓延的信号 |
| 「你看着办」 | 放弃了需求澄清 |

---

## 5. 什么情况下需要先澄清

**必须澄清**（停下问，不要动手）：

- 需求本身模糊（业务规则不清楚）
- 后端契约缺失或不全
- 涉及新模块 / 新接口 / 新表 / 新页面设计
- 跨层、跨多文件的大改动
- 与 C 端共用文件的改动（涉及双向下发）

**不必澄清，直接做**（本项目既定规则）：

- 单文件或少量文件的改动（改字段、修明确 bug、新增小方法、样式文案）
- 需求明确无歧义，不涉及新模块/新接口设计
- 已有模式的复制扩展（照抄既有写法）

> 判断不明确时 → **按简单改动处理，先向用户确认一句再动手**。
