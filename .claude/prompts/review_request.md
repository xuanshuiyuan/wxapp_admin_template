# prompts/review_request.md — 评审请求提示词

> **用途**：调用 `reviewer` / `security_agent` 时的提示词片段。
> **核心原则**：**说清范围、说清排除项** —— 否则评审会淹没在噪音里。

---

## 1. reviewer（代码评审）

### 1.1 基础用法

```
reviewer 审一下当前 git diff，按阻断项 / 建议项分级，结尾给结论（通过 / 打回）。
```

### 1.2 指定范围

```
reviewer 审 src/services/http/request.js 与 src/services/session.js 的耦合，
重点看注册模式是否引入了时序风险。
```

### 1.3 明确排除项（减少噪音）

```
reviewer 审本次改动。
排除：样式微调、注释措辞、命名偏好 —— 这些不用报。
重点：分层合规、红线违反、变更登记完整性。
```

### 1.4 要求逐条核红线

```
reviewer 逐条核对 .claude/CLAUDE.md §9 的 18 条红线，
每条给「过 / 不过 / 不适用」，不要只回"没问题"。
```

### 1.5 高要求模式（发布前）

```
reviewer 做发布前评审：
1. 阻断项必须给出 file:line + 依据条款
2. 列出「已核对通过项」（让我知道你真看了）
3. 列出「未审查范围」（让我知道盲区）
4. 确认回滚方案是否可执行
```

## 2. security_agent（安全审查）

### 2.1 基础用法

```
security_agent 扫一遍当前 diff，重点：密钥泄漏、敏感信息暴露、鉴权绕过。
每条给：等级 / 位置(file:line) / 证据 / 攻击者能做什么 / 修复建议。
报告里引用密钥或手机号必须打码。
```

### 2.2 针对性审查

```
security_agent 审 services/session.js 的登录链路：
1. authRetry:false 是否在所有登录/绑定接口上都传了
2. 重登失败是否安全退化（清理了响应式态？）
3. 是否有任何路径会让 token 进日志
4. `VITE_MOCK_LOGIN_CODE`（非微信端联调通道）的风险面
```

### 2.3 守卫豁免审查（本项目高频问题）

```
security_agent 逐一评估本次改动里所有 guard: false 的使用点：
- 每个使用点是否属于「守卫目标页自己的接口」或「失败即隐藏的装饰位模块」？
- 有没有为了「别弹框打扰我」而滥用的？
滥用 = 绕过了登录态/账号态检查，属阻断项。
```

### 2.4 发布前扫描

```
security_agent 发布前扫描：
1. VITE_API_KEY 是否出现在 src/ 或产物里
2. grep localhost:15200 dist/ 是否为空
3. .env.*.local / dist/ / unpackage/ 是否被误提交
4. 有无明文 http:// 请求地址
5. 错误 msg 是否含内部结构（堆栈/SQL/表名）
给出「已检查范围」清单 —— 让我知道哪些没查。
```

## 3. 并行评审（独立视角）

```
请并行做两件事，结论分开给我，不要合并：
1) reviewer 审代码质量与分层合规
2) security_agent 审安全面
两份报告都保持各自的结论，即使有冲突也如实呈现（冲突本身是信息）。
```

---

## 4. 评审后的处理

| reviewer 结论 | 处理 |
|---|---|
| **通过** | 继续流程 / 合入 |
| **有条件通过** | 记下建议项，**可延后**，但必须登记到 `known_issues.md` |
| **打回** | 按阻断项归属退回对应阶段重做，**不许带病前进** |

**打回后的复评**：

```
reviewer 复评：上次的 3 个阻断项已按建议修改，只复审这 3 项 +
确认修改未引入新问题（尤其没有顺手扩大范围）。
建议项本次未处理，仍保持"建议"状态。
```

---

## 5. 反模式

| ❌ | 为什么差 |
|---|---|
| 「审一下」 | 没说范围，评审会发散 |
| 「审一下，没问题的话就合了」 | 预设了结论，会诱导放水 |
| 「严格审，一个问题都别放过」 | 会导致风格偏好被当成阻断项，失去可信度 |
| 「不用太细，大概看看」 | 那就不必评审 |
| 让 reviewer 顺手改 | reviewer 是**只读**的，改代码会失去独立视角 |

## 6. 关于「阻断项 vs 建议项」的期望管理

`.claude/agents/reviewer.md` 的判定口径：

**阻断**（必须改）：红线违反 · 业务逻辑在页面 · 契约字段无出处 ·
结构变更未同步 `CLAUDE.md` · 业务规则变化未更新 `business-logic.md` · 真重要变更未在 commit message 写一行 · 静默吞异常 · 重造已有能力。

**建议**（可延后）：命名/注释风格不一致 · 可以更好但当前正确。

**不算问题**：未确证项**已如实标注**（诚实即可，不阻断）。

> **如果报告里什么都成了阻断项，说明口径失控了** —— 可以这样要求：
> 「阻断项必须引用 .claude 里的具体条款，不要引用个人偏好。」
