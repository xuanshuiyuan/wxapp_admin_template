# rule-performance

本工程的性能约定。**第一原则：不要过早优化** —— 先有可观测症状与测量数据，再动手。


> 移植时**剔除了源工程业务实例**（轮询 / 天气 / 定位）。
> ⚠️ **模板现成实现只有两处**：`services/session.js` 的 `login()`（同 key 单飞）与
> `http/guard.js`（同码动作去重）；`useList` 只做分页，**没有** SWR / 规范 key 归一。
> 三件套是「新项目按需实现」的机制说明，不要把「文档写了」当成「代码已有」。

## 硬性禁令（MUST / MUST NOT）

> **本节是本主题 MUST / MUST NOT 的唯一权威。**

- ❌ 禁止一次性加载大量数据到前端（**必须分页**；几千条用 uview 的 `u-list` / `u-virtual-list`，见 `rule-ui-components`）
- ❌ 禁止在循环中发起网络请求（能合并接口就合并，不能合并改并发 `Promise.all` 并控制批次）
- ❌ 禁止频繁触发重渲染（模板里调方法、逐字段改 reactive 大对象都算）
- ❌ 禁止无索引的全表扫描（后端预留）
- ❌ 禁止在日志中打印大对象（与 `rule-security` 的日志脱敏同条）
- ❌ **禁止在没有测量数据的情况下优化**（见下方「先测量再优化」）

## 0. 先测量再优化（本工程第一原则）

⚠️ 模板目前只有 7 个页面且都是演示量级数据，**还没有真实性能问题**；下面的规则是接入业务后的检查口径，不要拿「没数据」当免检理由。
本规则的作用是**防止埋下性能债**，不是让你去优化不存在的瓶颈。

**动手前三问**：

1. 有**可观测的症状**吗（卡顿 / 白屏 / 超时 / 包体积超标）？
2. 有**测量数据**吗（小程序开发者工具的性能面板 / 体验评分）？
3. 改动能**被验证**有效吗？

任一为「否」→ **不要优化**，写进 `.claude/memory/known_issues.md` 观察即可。

> ❌ **反例**：因为「虚拟列表更快」就给一个 20 条的列表上虚拟滚动 ——
> 徒增复杂度，且引入新的正确性风险。

**做缓存前额外三问**（本工程特有 —— 缓存是最大的过度设计来源）：

1. 数据变化频率 **>>** 读取频率吗？（如字典、配置 → 可缓存 + 标明 TTL）
2. 是「**用户状态类**」数据吗（权限 / 账号态 / 余额）？→ ❌ **不缓存**，**必须以服务端为准**。
   先例：会话里的 `permission` 是**登录时快照**（最长 2h 才刷新），本工程**只拿它做显隐**，
   真正的准入一律看服务端（无权回 `40102`，调用方必须处理）——
   把快照当"一定调得通"的凭据就是典型的越权隐患（`services/storage.js` 的 `getPermission` 注释）
3. 缓存**失效条件**说得清吗？说不清 → 不要缓存

## 1. 前置：小程序的性能模型（与浏览器不同）

| 维度 | 小程序 | 浏览器 |
|---|---|---|
| 运行时 | **双线程**（逻辑层 + 视图层） | 单线程 |
| 数据同步 | **跨线程通信，是主要瓶颈** | 无此概念 |
| 首屏 | 包体积 + 冷启动影响大 | 网络 + 解析 |
| 长列表 | `scroll-view` **全量渲染**会卡 | 可滚动回收 |

**本工程跨端统一写法**（`scroll-view` + `refresher`）在小程序端**全量渲染**，
故长列表需注意；`useList` 已做分页（默认 `page_size=20`），**不要一次拉全量**。

## 2. 渲染

- **列表必须分页或虚拟滚动**（`useList` 已封装触底加载，见 `rule-add-page`）
- 复杂计算用 `computed` 缓存；**避免模板中调方法**
- `v-if` / `v-show` 按重渲染代价选
- **减少跨线程通信**：❌ 禁止在高频回调（`touchmove` / `scroll`）里做大对象赋值。
  ✅ 本工程范例：`usePullRefresh` 在 `@touchmove` 里只更新一个 `offset` **数值** —— 照抄这个做法
- ❌ 禁止把整个大响应体绑到模板上（只绑用到的字段）。
  ✅ 范例：`useList` 回传 `body`（最近一次原始响应）给「后端附带字典」场景用，
  **但不绑到模板**，页面按需取
- **减少 WXML 节点数**：四态手写已被 `app-list-state` 收敛成一个组件

## 3. 网络

- **合并请求**减少 HTTP 次数；互不依赖的取数**并发**（`Promise.all`），不串行
- ❌ 禁止在循环中发请求
- **图片**：走 CDN + 合适尺寸（`u-image` 自带失败兜底）
- **合理本地缓存**（`services/storage.js`）

### 3.1 ★ 同一份数据的重复请求：去重三件套

「按 key 轮询」和「按事件刷新」这两类最容易写出**连点打爆后端**。
三件事各管一段，**缺一就有真实事故**：

| 手段 | 怎么做 | 治什么 |
|---|---|---|
| **① 新鲜期窗口（SWR）** | 缓存条目带 `at` 时间戳；`Date.now() - at < interval` 视为新鲜 → **直接吃缓存不发请求**；陈旧则「先吃缓存渲染 + 后台静默重拉」（滑动零等待） | 高频切页 / 反复进页把同一个接口打爆 |
| **② 同 key 单飞** | `inflight[key]` 存进行中的 Promise，同 key 再来直接 `return` 它；`finally` 里删。**普通对象即可，无渲染语义的东西不要塞进 `ref`**（否则每次请求都触发重渲染） | 快速连点时同一份数据各发一次；**带频控的接口尤其致命**（如绑定接口连点会撞 `58003`，同手机号 60s 内失败满 5 次就锁窗口） |
| **③ 规范 key（canonicalKey）** | 首屏「不带参数」（后端默认取最新那条）请求回来后，**用响应里的真实 id 把缓存与当前 key 归一**，此后轮询/下拉都带它 | 后台刷新把用户正在看的那条跳回「最新的」；缓存挂在两个 key 上白白翻倍 |

**本工程已有的现成实现**（照抄，别自创）：

| 位置 | 实现了哪几件 |
|---|---|
| `services/session.js` 的 `login()` | **② 同 key 单飞** —— `pending` 缓存 Promise，并发补会话只真登录一次 |
| `services/http/guard.js` | **② 单飞 + 冷静期** —— busy 去重 + 1s 冷静期，并发命中同一守卫码只弹一个框 |
| `useList` 的 `loading` 守卫 | **② 在飞判重** —— `if (loading.value) return` |
| `usePullRefresh` 的 `can` | **② 在飞判重** —— `can: () => !loading.value` |

> ⚠️ **不要重复造**：请求链与守卫层**已经有**单飞机制。
> 你要新增「按 key 取数」的能力时再补 ① 与 ③。

**配套口径**（都是定稿，别再自创）：

- **新鲜期长度对齐后端频控**：窗口内重拉拿到的也是同一份数据，只会白烧频控额度。
  本工程已知频控：绑定接口 `admin/login/bind` —— 同手机号 **60s 内失败满 5 次**回 `58003`
  （常量 `BIND_COOLDOWN_SECONDS`，处置是**页面置灰倒计时**、**不自动重试**，刻意不进全局守卫）。
- **常驻定时器能省就省**：不做秒级 ticker 自己算「x 秒前刷新」；
  能取接口给的值就取。轮询必须 **`onShow` 起、`onHide` 停**。
- **装饰性数据失败静默**：非主干展示位恒 `{ toast: false }`，**失败保上一次旧值**、
  字段残缺也不覆盖旧值，**更不参与页面错误态判定**（宁可显示旧数据也不闪空、不弹错）。
  ⚠️ 本工程**当前无现役先例**：`pages/admin-home` 的 `refreshBound()` 已随 v1.0.0 的「绑定态展示」**删除**；口径仍生效，将来做装饰位时照此办。
- **会话级缓存的适用面**：结果不随页面变化、且取一次代价高的东西缓在 `services/` 模块作用域；
  **有渲染语义的状态才进 `store/`**。
- **并发而非串行**：互不依赖的取数一起发，指示器等到**两者都结算**再收。

## 4. 启动与包体积

- **首屏关键路径要短**：`App.vue` 的 `onLaunch` 只做静默登录（必要），**不塞非必要初始化**
- ⚠️ `main.js` 的两条副作用 import **不可删**（`@/services/session` / `@/services/guards`）
  —— 它们是**注册**动作，成本极低但删了会丢失关键机制
- ❌ **禁止在启动路径同步读大量本地存储**（`getStorageSync` 是同步阻塞）。
  本工程 `SESSION_FIELDS` 是白名单、字段少 —— **不要往里加非会话字段**
- **图片**：❌ 禁止把大图打进包（小程序主包限 2MB / 总包 20MB）。
  ✅ 走 OSS（`utils/oss.js` 的 `ossUrl()` 拼 `VITE_OSS_HOST`）+
  **必须指定合适尺寸** + **必须有加载失败回退**（先例：`app-loading` 的
  `LOADING_IMAGE` + `LOADING_IMAGE_FALLBACK`）
- **分包**：页面变多时用 `pages.json` 的 `subPackages` + `preloadRule`（本工程尚未启用）
- ❌ 禁止引入未评估体积的新依赖（本工程 `dependencies` 仅 `vue` + `blueimp-md5`）

## 5. 样式性能

- ❌ 禁止在 `scroll-view` 内用大面积 `box-shadow` / `filter` / 半透明叠层（小程序端重绘成本高）
- 动画优先 `transform` / `opacity`（可合成），避免 `width` / `height` / `top` / `left`
- ❌ 禁止深层嵌套选择器（SCSS 嵌套 ≤3 层）

## 6. 后端（跨模块 / 未来后端预留）

> 本工程无后端，后端代码不在本仓库。以下供将来参考。

- **数据库**：查询走索引；避免 N+1；大结果集分页；合理使用 Redis/Memcached
- **接口**：慢接口异步化；高并发考虑限流/降级
- **资源**：防内存泄漏；及时释放连接与文件句柄；使用连接池

- **`static/` 只放必要资源**（当前仅 `loading.png`）—— 这里的东西全进主包，主包硬上限 2MB，
